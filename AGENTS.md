# AGENTS.md

Guidance for coding agents (Claude Code, Codex, opencode…) working in this repository. **Keep this file current**: when you add a crate, a command, a convention or a gotcha, update it in the same change.

## What this is

xherd: a daemon (Rust) that runs, watches and steers many coding agents, each in its own git worktree and tmux session, with approval gates. Read before changing behaviour:

- `doc/internal/spec.md` — what (requirements `R-xxx`)
- `doc/internal/design.md` — how (crates, architecture, milestones §18, decisions §19)
- `doc/reference/xap.md` — agent protocol (`xherd hook|report|gate|task|commit …`)
- The final docs, by reader (index `doc/README.md`; layout and rules in `doc/dev/development.md` → Writing docs): `doc/user/` (`getting-started.md` for published releases, `guide.md` using xherd, `docker.md`, `security.md`), `doc/reference/` (`cli.md`, `configuration.md`, `http-api.md`, `xap.md`), `doc/extend/` (`plugins.md`, `flow-packs.md`, `integrate-your-sdd.md`), `doc/dev/` (`from-source.md`, `development.md`, `architecture.md`). They replace spec/design when those go; **update them in the same change as the behaviour they describe** (a new CLI flag → `cli.md`, a config key → `configuration.md`, a route → `http-api.md`, a user-visible feature → `guide.md`). `README.md` at the root is the presentation page.
- `ROADMAP.md` — what is left, by theme (the milestone checklist in `doc/internal/design.md` §18 stays the source of truth; update both)

Decisions in `doc/internal/design.md` §19 are settled; do not re-open them in code. Cite requirement ids (`R-009`) in doc comments where code implements one.

M0 (skeleton) and **M1** (one job end to end) are merged; progress is tracked as checkboxes in `doc/internal/design.md` §18. M1 was checked end to end with real Claude Code and `gh` (draft PR opened on a real repository). M1 scope decisions: approvals from the CLI only (the UI comes in M2); xherd v0 ships the `feature` flow only. `xherd new` / `POST /api/v1/jobs` create jobs (worktree + `.xherd/` + Claude Code hooks) that start: the built-in `claude-code` runtime plugin gives the launch argv (`claude`, permission mode `edits`, the default; `ask` is the strict one), the daemon starts it in a tmux session named after the job, and types the flow's start command once the runtime's `session-start` hook arrives. Approving a gate starts a **fresh session** (`freshSessions`, default on; R-023): the job window's process is respawned with `job.launch` and the next command is typed on the new `session-start`; with it off, the command is typed into the current session. Resume starts with the pack's `resume` command unless a next prompt is pending (R-027). Commit gates are reviewed with `xherd diff <job>` / `GET /jobs/:id/diff` before `xherd approve`; at the ship gate (`pr.md`) the same diff shows the branch as it will be pushed (`<job.base>...HEAD`). Approving the ship gate hands on `/xherd:ship`, and the **job** pushes and opens the draft PR (the daemon never pushes), then reports `xherd pr opened`; a flow job that stops idle with `pr_url` set and no gate, in the ship or a PR stage or in implement with every task done (the end of `pr-apply`), ends its session and goes to `watching` (R-301); a stop in another stage (sent back to review after the PR opened, maybe waiting on a background reviewer) keeps the session. Background-task guard (R-024, partly): a stop whose payload lists `background_tasks` with `status: running` (Claude Code's `Stop`; `report::background_running`) logs `background-running` and skips auto-approval and the move to `watching`, since ending the session would kill the task (a reviewer subagent was cut off that way and came back on the next resume); the stop after the task's result decides. A user approval while one runs still starts a fresh session (not guarded yet). Resume works from `watching` (back to `queued` with the pack's `resume` command, the PR stays). If it stops in the ship stage without reporting one, the daemon asks the host plugin (`pr-for-branch`, built-in `github` through `gh`; R-302). `xherd ls` shows the PR once no gate is open. The ship stage has no auto-approved variant any more (the `autoApproved` field stays in the pack format); the pre-push guard (R-1204) is a guardrail (M4) and PR polling is PR follow-up (M4); code tripwires on commits (R-115…R-117, incl. the secret tripwire) and `diff_viewed` marks are M4/M2. Not done yet: pause with a handoff (R-026, pause just ends the session), runtime change between steps (R-025, one runtime), resuming the runtime's own session.

Git access block (R-688): `xherd_core::git_auth::failing_line` recognises auth failures (git, ssh, `gh`). `Actor::git_access_failed` runs on the `ScreenScan` capture of a **running** job only (a stopped job's screen is its own prose: a job at the pr-review gate that wrote "run the same gh auth login" was blocked and could not be approved), with `failing_screen_line` (no `gh auth login`/`glab auth login` hints; a failure line that stays on screen blocks once, `auth_screen_line`; a git-access block at an open gate left by an earlier build is cleared by the scan once no failure shows, `auth_screen_block`; clearing returns a job with a gate to `waiting-input`, not `running`) and on `pr-poll`/`pr-lookup` errors: a live job gets `Blocked` with `Job.block_reason = "git access"` (cleared when it leaves `blocked`; a successful PR lookup clears it too), a watching one is only notified; event `git-access-failed`. The blocked band shows the doctor's first failure and fix: `GET /jobs/{id}/git-access` (`Daemon::agent_git_access`: host from the PR URL, else the worktree's `origin` through `remote_host`; then `git_doctor`) is fetched when the band shows a `git access` block, with a Check again button. Nothing is stored; the notification also names `xherd git doctor <host>`.

Live settings: `Env.settings` is a `SettingsHandle` (`actor.rs`; `get()` gives an `Arc<ActorSettings>` snapshot, take it once per use); `Daemon::save_config` rebuilds it with `ActorSettings::from_config` (config-derived fields over the start-time base: binary, URL, `screen_rules`, sandbox flag, `Options::pr_poll` override). Only `port`, `bind`, `maxConcurrentAgents`, `workspace`, `tmuxSocket`, `pluginSettings` need a restart (`Config::apply_live_from` lists the live fields; `config_view`'s `restartNeeded` compares the rest). Wherever AGENTS.md below says a setting is "read at daemon start into `ActorSettings`" or "applied at the next start", it is live now; the budgets, tripwires and limits are read from the snapshot on each use. A setting that must stay live needs its field in `from_config` and `apply_live_from`. `disabledPlugins` is in the snapshot too: `Actor::host()`, the trust writer and the toolchain plan skip a disabled plugin.

Board (`#/board`, `pages/Board.svelte`, read-only): units of work in Pending / In progress / Done. A unit is a flow stage (labelled by its `label`, else its **role**, R-210, through `stageLabel`; state from `flow::steps`: passed = Done, a skipped one says so, a later stage already visited says "again after the fixes"), or, once the job has tasks, each task in place of the flow's first implement-role stage (a later implement-role stage, bugfix's Fix after Reproduce, gets no card of its own; `blocked` stays In progress with its reason; `source` review/pr shows a tag). Flow `none` = one card per job; cancelled jobs are left out. The card where the job waits for you is outlined with `--gate` (a commit gate marks its tasks); a pending task says which unfinished tasks it waits on (`depends`); the job's colour (`agentHue`) is on the lane title, or on each card without lanes by job. Swimlanes `?lanes=` none (default: every card together) `|job|repo|flow` (`lib/board.ts`: `boardLane`, `todoLane`, `laneOrder`; by workflow = Feature, Bugfix…, No workflow, TODOs last); filters `?job=NAME`, `repo=NAME`, `needs=1` (only outlined cards and due TODOs), `finished=1` (done and watching jobs and TODOs completed over a day ago, hidden by default), `upcoming=0|1` (stages not reached yet; default on only with lanes by job; off still shows each job's next stage). TODOs are cards in the same columns (in their own lane with swimlanes): scheduled = Pending, due or check failed = In progress and outlined, completed = Done; hidden by the job and repository filters. On a phone (< 760px) the filters fold behind a Filters button and one column shows at a time (a switch above the lanes, In progress first). Auto-approved stages are not marked (the job state does not say which gates were auto-approved). The jobs by stage are on the Herd: `?layout=stages` (`components/StageColumns.svelte` over `lib/stageLanes.ts` `stageLanes`: one lane per workflow of the jobs shown, unlabelled when there is only one, No workflow last; each lane has its flow's stage columns in flow order (`stageLabel`) plus Not started (when used), Watching PR and Finished, with a count per column; the Herd's filter applies). Not there: per-pack card declarations (R-1101: record source, title, column mapping), which need profiles/pack `views`. Needs attention (`#/attention`, `pages/Attention.svelte`, `lib/attention.svelte.ts`): jobs waiting for you (`needsYou`, the `NeedsCards` the Herd shows too), TODOs `due` or `error`, and unseen auto-approvals (R-111); the bar's link shows ✋ and their count when any is pending (on a phone it reads "Attention" and comes right after Herd, so the count never scrolls away) (`/todos` and `/reviews` refetched every 30 s and after Mark seen). There is no list of jobs outside the Herd (the strip under the bar is gone). Time (`#/time`, `pages/Time.svelte`, `xherd_daemon::worklog`, spec §16.4): the minute tick books the span since the last flush (`Daemon.worklog_flushed`, capped at 2 min) to every `running` job's ticket as kind `agent` in the `worklog` table (UTC day); the job page posts `POST /jobs/{id}/user-time {ms:30000}` every 30 s while visible and focused (kind `user`, clamped to 2 min per call). `GET /worklog?days=N` returns per-day rows and per-ticket delivery metrics: cycle time (created → `done`, from `status_since`), `review_rounds`, auto-approvals and rework (auto-approvals followed by a `change-request` event with the same gate label; `request_changes` logs that event; `worklog::rework`). Job time is not booked while the daemon is down.

TODOs (`#/todos`, `pages/Todos.svelte`, `xherd_core::todo` pure lifecycle `open → checking → due → done | error`, `xherd_daemon::todos`, table `todos` as JSON): reminders due at a time, once or repeating (`repeatMinutes` ≥ 5; completing a repeating one jumps to the next time after now), and **condition checks** (spec §16.2): a TODO with a `condition` (words) and `repeatMinutes` = the check interval is checked at each due time. `Daemon::todo_tick` runs on the 30 s poll tick: a TODO whose time has come becomes `due` and publishes `Change::Notify {agent_id: "todo:<id>", kind: "todo"}` once (skipped when `todo` is in `mutedNotifications`; the UI opens `/todos` for such notices). API: `GET/POST /todos`, `PUT/DELETE /todos/{id}`, `POST /todos/{id}/complete`, `POST /todos/{id}/reschedule {due}`. They are not jobs and never count against the cap (R-006). A check (`Daemon::spawn_check` / `run_check`, `POST /todos/{id}/check` = "check now") is one headless run of the default runtime as the agents' user (`Cmd::as_agent`, cwd = the workspace, `CHECK_TIMEOUT` 2 min): the runtime plugin's `data.terminal.check` (`xherd_plugin::runtime::Check`: `argv` with `{prompt}` and `{system}` once each, optional `modelArgs` with `{model}`; Claude Code: `claude -p … --allowedTools` read-only tools and `gh`/`git` read commands, `--disallowedTools Edit Write NotebookEdit`, `--no-session-persistence`; a runtime without `check` cannot check, the TODO goes to `error`). The run must end with `XHERD_RESULT {"met": bool, "summary": "…"}` (`todo::parse_result`, last such line wins): met or no/unclear answer or timeout → `due` (notified, you look), not met → `open` at the next interval, run failed → `error`; a check lost to a restart (`CHECK_STALE_MS`) becomes `error`. The summary is model output: shown on the page, never in notifications. `model` is validated to plain characters (it goes on a command line). Keep any new `check` argv read-only: that is the only thing that makes a check safe.

Shared memory (spec §16.6, #65): `memory.md` is one job's; the repo's `AGENTS.md` is shared by every later job. The review prompt (step 6) may write the whole proposed `AGENTS.md` to `.xherd/AGENTS.proposed.md` and call `xherd memory propose --reason …` (`XapCmd::MemoryPropose`, `xherd_flow::xap::{MEMORY_PROPOSAL, MEMORY_MAX_BYTES}`); `Job.memory_proposal` holds one, replaced by a new call. Job page → Shared memory (`panels/Memory.svelte`, `GET /jobs/{id}/memory` = `Daemon::memory`: proposed text, current `AGENTS.md`, the `CLAUDE.md` an accept would write) shows the diff and an editor; `POST /jobs/{id}/memory-accept {text?}` (`Actor::memory_accept`) writes `AGENTS.md` and, when the `@AGENTS.md` import is missing, `CLAUDE.md` (`xherd_flow::memory::claude_md`, content kept), and commits both with `commit_paths` (the accept is the approval, like a commit gate; refused while `running` or once `pr_url` is set, xherd never pushes); `memory-dismiss` drops it and, if the repo has no `AGENTS.md`, records `memory_declined` (repo, `AGENTS.md`), after which `memory propose` is refused there until the repo has one. A proposal never blocks the flow; the your-call band links to it.

Welcome (`pages/Welcome.svelte`): Welcome (with where it runs), Plugins, Commit identity, Git access, Connect & check, Ready (XHERD-1). Entering step 5 runs the checks again (`loadChecks` keeps the old results while running), and a git login that ends in `GitHosts` does too (`onlogin`). One plugin view for Welcome step 2 and Settings → Plugins: `components/PluginList.svelte` (search box, broken plugins, Enabled and Available sections grouped by kind, cards with switch, state, Log in and Options; pure helpers `KIND_LABEL`/`KIND_ONE` (kind `host` reads "Git providers"/"Git provider"), `OPTIONAL_KINDS`, `lastOn`, `matches`, `needLogin` in `lib/plugins.ts`, tested). Options and every Log in open `PluginDetail` as a `Dialog` (≤ 680px) holding the only plugin-login terminal; Settings keeps `?plugin=<name>` in the URL; `Dialog` ignores Escape typed inside `.term`. Git access is two components, `GitIdentity.svelte` (name, email, per-owner identities; its own save bar) and `GitHosts.svelte` (hosts, doctor; its own save bar), stacked in Settings → Git access; `heading` hides the section title where the page has it (Welcome), in Welcome both also take `bar={false}` and expose `save()`/`saveAll()` plus bindable `unsaved` (and `ready` for the identity): steps 3 and 4 have one button, "Save and continue" when something is edited, and step 3 waits for a name and email; `GitconfigNote.svelte` is the native-run "include this gitconfig" note (above the identity, and above the hosts unless `note={false}`). Every card shows a state (`pstate` in `PluginList.svelte`: Off, Ready, or Not ready with the first failing check's text, `–` for an optional check) and an Options button that opens `components/PluginDetail.svelte` (settings with their own save, the plugin's checks with fixes, the language versions in the container, and a note that native runs never install languages, R-653). `PluginDetail`'s settings save on their own, replacing that plugin's object, so an emptied field is cleared (the Settings save bar does not cover plugins), and the dialog handles its own login. Each toolchain plugin has an optional "manager found" check (never required, so it never blocks: `required` is only true for the default runtime), so a language card says Not ready with an install link when its manager is missing; in the container a Ready language card adds "versions install on first use" (no installed-versions list: the manifests have no command for that). Trackers (`xherd_plugin::tracker::Tracker`, `data.tracker.links`): built-in `jira`, `github-issues`, `gitlab-issues` only turn text into links (`Daemon::tracker_links` → `/state` `trackerLinks`, `ui/src/lib/links.ts` applies them to rendered Markdown after sanitising and to the ticket pill on the job page; https only, patterns checked when the manifest loads). No tracker may be on. Reading (`xherd_plugin::issues`, `Host::ticket_get`, `Daemon::agent_ticket`, `GET /jobs/{id}/ticket`, `panels/Ticket.svelte`): `data.tracker.key` (one group = the issue reference, plain name) and `hosts` choose the tracker for a job's ticket key and the origin host (`tickets::pick_tracker`); `github-issues` runs `gh issue view --json …comments`, `gitlab-issues` `glab api` on the issue and its notes; external trackers answer `ticket-get`; `jira` reads through `acli` (`issues::jira_view` and `adf_to_markdown`: Jira's REST shape with ADF text, a flat object and a bare comment list are accepted; `acli jira workitem view --json` was checked against real output (Jira's REST shape; its `self` is an internal Atlassian host, so the ticket link comes from the plugin's `baseUrl` setting only); `comment list --json --paginate` was checked too: one JSON document per page back to back (`merge_comment_pages`), `author` and `body` are plain strings, there is no timestamp so the CLI's order is kept. `acli` is not installed here; the container install downloads a pinned `acli` (version and per-architecture sha256 in the jira manifest's `install`: Atlassian publishes no checksums, so they were taken from the files at pinning time; bump all three together) and was checked outside the container only; `acli --help` as the presence check is untested). Posting (R-308): the ship prompt no longer touches the ticket (a `## Ticket update` section in `pr.md` would have ended up in the public PR body, and would tie the feature to one pack); once `Job.pr_url` is set, `components/TicketPrompt.svelte` on the job page offers a summary (`GET /jobs/{id}/ticket-status`: tracker and whether the event `ticket-comment` exists; "Not now" is kept in localStorage) that opens the Ticket tab with the draft (`?s=ticket&draft=1`). The Ticket tab drafts a summary (`xherd_core::ticket::summary` from finished tasks, commits, the PR; `GET /jobs/{id}/ticket-summary`), the user edits it and `POST /jobs/{id}/ticket-comment` posts that text (`Host::ticket_comment`: `gh issue comment`, `glab api` notes, `acli … comment create`, or the external `ticket-comment`; marker on GitHub/GitLab; event `ticket-comment` with the length only, kept past `eventRetentionDays` (`xherd_store::KEPT_EVENTS`) so the prompt never comes back); nothing is ever posted without that click, and there is no automatic posting. Checked with fake CLIs only (a real post was never made; Jira's handling of newlines in `--body` is unknown). Reading is read-only; the text is sanitised in the UI and rendered with `render(…, external = true)`, which keeps only an allow-list of Markdown tags and attributes (DOMPurify's defaults keep `background=` and SVG `feImage`, which load by themselves) so nothing in it loads by itself and must be wrapped (`untrusted::wrap`) if ever given to a job. Checked against real `gh` (an issue of this repo, no comments) and fake `gh`/`glab` scripts; GitLab and comments against the real CLIs not checked. Plugin manifests have `requires` (R-691, `manifest::Requirement`: a tool as the check `requires:<name>`, `install` argv offered in the container as a `Fix::Session` run by `Daemon::start_plugin_install` in the plugin-login terminal, `instructions` by OS shown natively; `install` must be a program on `PATH`). Plugin secret settings (`secret: true`) are edited in the plugin's options (`GET/PUT /plugins/{name}/secrets`: write-only, only declared keys, stored in `secrets.json`; `Daemon::plugin_context` and `actor::with_git_token` read them from disk, so a saved secret applies at once; plain settings still need a restart). Toolchain managers use `requires` for their "manager found" check, and a tool's optional `installed` argv (`Daemon::toolchain_installed`, `GET /toolchains/installed`) lists installed versions for the options page and the Welcome language cards (`uv` lists every interpreter it finds, system ones too; the commands are unverified in the container). The runtime plugins declare their CLI with `requires` (check ids `plugin:<runtime>:requires:<cli>`, required for the default runtime as before); the container install is `npm install -g --prefix "$HOME/.local" <pkg>@<version>` with the Dockerfile's version (`runtime_installs_use_the_image_versions`). Not done: reviewing an external plugin's install argv before it runs (needs the install-from-GitHub flow, R-542).

## Running it

```sh
XHERD_HOME=/tmp/xh cargo run -p xherd-cli -- daemon     # JSON logs on stderr; XHERD_LOG=debug for more
XHERD_HOME=/tmp/xh cargo run -p xherd-cli -- status
XHERD_HOME=/tmp/xh cargo run -p xherd-cli -- install  # /xherd:* commands into ${CLAUDE_CONFIG_DIR:-~/.claude}/commands/xherd/
```

No trust step is needed: xherd marks each new worktree trusted in Claude Code's config. Claude Code must be logged in (`claude`, then `/login`, once).

In Docker, everything inside the container (daemon, UI, tmux, Claude Code, toolchains), only the workspace shared:

```sh
cd deploy/compose
printf 'XHERD_WORKSPACE=%s/xherd\nXHERD_UID=%s\nXHERD_GID=%s\n' "$HOME" "$(id -u)" "$(id -g)" > .env
mkdir -p ~/xherd && docker compose up -d --build     # http://127.0.0.1:4740/
```

The UI (needs Node and pnpm; cargo does not run it):

```sh
cd ui && pnpm install && pnpm build     # ui/dist, served by the daemon at http://127.0.0.1:4740/
cd ui && pnpm dev                        # Vite dev server, proxies /api to XHERD_URL (default 127.0.0.1:4740)
cd ui && pnpm check                      # svelte-check (types)
```

Data root: `XHERD_HOME`, else `$XDG_DATA_HOME/xherd`, else `~/.local/share/xherd`. `config.json` there holds the port (4740), `tmuxSocket` and the generated user token used by the CLI.

## Build and test

Rust is installed through Homebrew's keg-only `rustup`; add it to `PATH` if `cargo` is missing:

```sh
export PATH=/opt/homebrew/opt/rustup/bin:$PATH
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
```

Integration tests need `git` and `tmux` (≥ 3.3) on `PATH`; tmux tests use a private socket (`-L xherd-test-…`) and never touch your sessions.

## Conventions

- Edition 2024, workspace lints: `unsafe_code = "forbid"`, clippy `all` = warn (CI denies warnings).
- External commands only through `xherd_core::exec::run` (argv, no shell, timeout + process-group kill, env allowlist, redaction). Exceptions: the interactive tmux client of a browser terminal (`xherd_term::pty`), still with an env allowlist; processes that replace the CLI (`toolchain exec`, `attach`, `shell`, `init` → daemon); long-lived helpers (`socat` in `init`, apps launched by `open`).
- State changes to a job only inside its actor, through pure functions in `xherd-core`; slow work returns as `WorkDone` tagged with the job's `generation`.
- `xherd hook` / `xherd report` must never print to stdout or exit non-zero, and must not start tokio (fast path, R-012, R-901).
- JSON on the wire and in files is camelCase; enum values are kebab-case.
- Files the daemon writes go through `paths::write_atomic`; secrets are mode 0600.
- Minimal code: no abstraction for a single use; flag unrelated problems instead of fixing them silently.
- Clean room: never copy or name proprietary tools, prompts, texts or design tokens from other products.

## Gotchas

- `target/` size: `[profile.dev] debug = "line-tables-only"` in `Cargo.toml` and `incremental = false` in `.cargo/config.toml` keep it small (about 30 test binaries each link the whole tree). Remove the second if rebuild speed matters more than disk; `cargo clean` is always safe.

- Agent → job rename (issue #141): what the code and docs called an agent is a **job**; "agent" is reserved for the saved setup of the next phases. `Job` (`xherd-core/src/job.rs`), table `jobs` (store migration 2), `/api/v1/jobs/…`, `XHERD_JOB_ID`/`XHERD_JOB_TOKEN`, `.xherd/job.json`, config `maxConcurrentJobs`/`jobTokenBudget`, backups under `jobs/<name>/`. Not renamed on purpose: `as_agent` and `XHERD_AGENT_HOME`/`XHERD_AGENT_PATH` (the OS user that runs sessions), the `xherd runner`, `AGENTS.md`, `memory propose`, the Herd view protocol v1 field `agents` (holds jobs). **Compatibility shims, remove in the next release:** the `410 moved` answer of `/api/v1/agents/{job}/…` (`gone_job`); `agentId` as an input alias in `Report`, `XapCall` and queued hook lines; the CLI's fallback to `XHERD_AGENT_ID`/`XHERD_AGENT_TOKEN` and `.xherd/agent.json`; tokens of kind `agent` in `AgentAuth`; config schema 4's read of `maxConcurrentAgents`/`agentTokenBudget` (`agent_keys_to_job_keys`) and the profile and settings alias `agentTokenBudget`; backup restore of `agents/<name>/` and manifest key `agents`; the `#/agents/<name>` UI redirect; `job.json` falling back to `agent.json` in `find_job`.
- Version (issue #53): `xherd_core::VERSION` is the Cargo version (compatibility checks, store, backups compare it; do not display-format it). `xherd_core::BUILD_VERSION` (`crates/xherd-core/build.rs`) is what people see (`xherd --version`, `/state` `buildVersion`, the bar next to the logo, Settings → About): the git tag of a release (`0.2.0`), `<tag>+<commits>.<hash>` after it, `<cargo version>+<hash>` before the first tag, `.dirty` for uncommitted changes, `dev` with neither git nor `XHERD_VERSION` (rules in `crates/xherd-core/version.rs`). `XHERD_VERSION` in the environment overrides it; the Docker image has no `.git`, so pass `--build-arg XHERD_VERSION=$(git describe --tags --always)`, or `XHERD_VERSION=dev-$(git rev-parse --short HEAD) docker compose up -d --build` (compose passes it as a build arg).
- Toolchain installs (issue #48): the install command is wrapped in `sh -c` that waits for Enter when it fails, so the terminal stays and shows the error; the version list is sorted newest first by `natural_cmp`.

- opencode (checked with 1.19): the TUI's input is not ready when plugins load (about 1 s later), so typed text is lost: deliver a session's first prompt with `promptArgs`, never by typing at `session-start`. `--prompt` is ignored with `--session` (use `resume.promptEnv`). `opencode export` through a pipe is cut at 64 KiB most of the time: export to `{file}`. The plugin runs in a worker (`process.argv` is not opencode's) and sees no TUI readiness event. Subagent sessions (`session.created` with `parentID`) must not report stops. The `permission.ask` plugin hook is never called; the `permission.asked` bus event is. The TUI remembers the last model used and prefers it to `model` in the config. The TUI submits `--prompt` before its command list has loaded when that is slow (a worktree's first start), so `/xherd/feature …` goes to the model as plain text (#145): the plugin's `chat.message` hook rewrites such a text part with the command's template (`client.command.list()`, rendered like opencode: `$1…$n`, `$ARGUMENTS`, else appended); test `crates/xherd-plugin/tests/opencode_plugin.rs` (needs `node`).
- tmux takes a new session's `PATH` from the client that creates it, not from `new-session -e PATH=…` (checked with tmux 3.6b): the jobs' `PATH` is the daemon's. Installed builds are fine (`/usr/bin/xherd` from the packages, `/usr/local/bin` in the image); a daemon run from source must have `target/debug` on its own `PATH`, or the prompts' plain `xherd …` calls fail with "command not found".
- `xherd hook` is handled in `main` **before** clap, inside `catch_unwind` with a silent panic hook, so bad arguments or panics still exit 0 with no output. Keep it that way.
- Sequence numbers from the CLI are `max(last + 1, now in µs)` (`.xherd/seq`), so counter-based and time-based reports from the same job stay ordered.
- Hooks without a token, or with the daemon unreachable / 5xx, are appended to `hook-queue.jsonl`; 4xx answers are not queued (a retry would not help). The daemon replays the queue at start and every minute.
- `rusqlite` is pinned to the version `rusqlite_migration` uses (both link `sqlite3`); bump them together.
- `ureq` 3 treats HTTP errors as `Err` unless `http_status_as_error(false)`; the CLI sets it.
- In axum handlers, read the peer address through the `ConnectInfo` extractor (not `extensions.get`) so `MockConnectInfo` works in tests.
- YAML is parsed with `yaml_serde` (the maintained serde_yaml). It expects `!Tag` syntax for enums; pack enums written as one-key maps (`Condition`) go through a raw struct with `try_from`.
- Pack manifests use `deny_unknown_fields`: fields not implemented yet (`views`, `extends`, `parse`…) are rejected, not ignored.
- XAP calls are de-duplicated by call id through the events table (`xap.<cmd>` events use the call id). A replayed call answers `{"changed": false, "duplicate": true}`.
- XAP observation (file reads, git) runs inline in the actor; keep it to small local reads.
- Gate documents are hashed with `xherd_flow::approve::doc_sha256`, never `content_sha256` directly: in the tasks-stage document the `- status:` / `- evidence:` lines of task sections, and whole task sections with `source: review` or `source: pr`, are dropped first (`tasks::without_progress`), so progress and the fix tasks a review or PR round adds do not re-open the tasks gate (R-107; otherwise `infer_gate` reopens Tasks at the first gate-less stop after the review). Use it at every place that records or compares a gate-document hash.
- Approval hashes what is on disk at approval time (the user approves what they read), not the hash recorded at `gate open`. Commit-gate files are recorded as `./<path>`; deleted files as `deleted`.
- On start the daemon re-imports every job's `approvals.jsonl` into the table (`INSERT OR IGNORE`): the file wins.
- A fresh session respawns only the `agent` window (`respawn-window -k`); the tmux session, its environment (`XHERD_*`, the job token) and other windows stay. The new process gets the variables because `new-session -e` puts them in the session environment.
- The daemon writes only the progress lines of job documents (D11, relaxed): after a successful `task start|done|block` the task's `- status:` (and `- evidence:`, one line, newlines joined with ` | `) in `.xherd/spec/tasks.md`; after `commit propose|done|drop` and the commit made on approval the entry's `- status:` / `- sha:` in `commits.md` (`xherd_flow::progress`, called from `Actor::write_progress`). Nothing else is touched, no entries are created; a missing file or entry is skipped (debug log), never an error. Task blocked reasons have no line in the format and are not written.
- `task done` runs the task's `verify:` in the daemon (R-118, `Actor::run_verify`): `sh -c <verify>` in the worktree through `exec::run` (the daemon's allowlisted env; the job could run the same command anyway), limit `ActorSettings::verify_timeout` (10 min; `Options::verify_timeout` for tests). It is a deliberate inline exception to "slow work returns as `WorkDone`", like `commit_for_user`: the job waits for the answer anyway. The result reaches the pure `xap::apply` as `Observed::Verify`; replayed call ids never rerun it (`on_xap` checks the id first), and a task already done is not re-verified.
- `gate open` and `commit propose` of an xherd flow need a valid `.xherd/spec/memory.md` (`xherd_flow::memory::check`, called from `Actor::observe`, refusal `memory_invalid`): the four `##` sections and at most 80 lines, nothing else. Tests that open gates get a valid one from `setup` in `tests/xap.rs`.
- Approving a parked job stores the next command in `job.next_prompt` and queues it; it is typed at the next `session-start` hook, like a new job's first command. Every other action on a parked job must also work, since it has no session to type into: Resume queues it with the pack's `resume` command (the gate stays open), and Send / Request changes store their text in `next_prompt`, unpark it and continue the last conversation when the transcript is found (`Actor::unpark_with`); a Send while a question is open still answers it. Pause and Cancel work as usual.
- Worktrees live at `<workspace>/worktrees/<repo dir name>/<job>`; workspace = `config.workspace`, else `$XHERD_WORKSPACE`, else `~/xherd` (design §8.1). Tests must set `workspace` in `config.json` or they write to the real `~/xherd`.
- Runtime trust (design §4.1): `TrustWriter` (`create.rs`) sets the runtime plugin's `data.terminal.trust` key for the job's worktree only (paths under `<workspace>/worktrees`, as stored and canonicalised), at creation and in `Actor::session_argv` before every start; other keys are kept and a non-JSON file is never overwritten (`runtime_trust`). Tests that create jobs must point `trust.file` of the built-in `claude-code` manifest at a fixture (see `tests/create.rs` setup), never the real `~/.claude.json`.
- A repository URL becomes `<workspace>/repos/<host>/<owner…>/<repo>`; https and ssh forms of the same repo share one clone. Clones and fetches run with `GIT_SSH_COMMAND` in batch mode (`xherd_git::NO_PROMPT`), so a missing key or host key fails instead of hanging. `new_agent` clones before its other checks, so a refused job still leaves the clone (reused next time).
- Pre-push guard (R-1204): each worktree gets `.xherd/hooks/` as its own `core.hooksPath` (`extensions.worktreeConfig` + `git config --worktree`), holding symlinks to the repo's other hooks (so they still run) and a `pre-push` that pipes git's stdin to `xherd guard pre-push` and then to the original `pre-push`. `git push --no-verify` skips it: it stops mistakes, branch protection on the host is the real boundary. Test: `crates/xherd-cli/tests/push_guard.rs` (real git, bare remote).
- Secret tripwire patterns live in `xherd_core::tripwire` (prefix + character class + minimum length, at a word boundary; `.env`-like files flag any non-empty, non-placeholder value). Findings are masked to four characters; never put the matched text in a message.
- `.xherd/` is excluded through the repo's shared `.git/info/exclude` (one line covers every worktree).
- A new job's first command (the flow's `start`, or the prompt for flow `none`) is stored in `job.next_prompt` and typed when the runtime's `session-start` hook reports, with the pack's `slashEnters` when it starts with the pack prefix. No hook (e.g. the runtime shows a dialog: `xherd attach NAME` and answer it) = nothing typed yet. The command stays in `next_prompt` until the runtime accepts a prompt (`user-prompt-submit`, `Actor::first_unacked`): Claude Code 2.1.319 fires `SessionStart` twice about a second apart and drops text typed after the first, so every `session-start` before the ack types it again.
- The runtime's hook file (`.claude/settings.local.json`) is written at creation, not at each launch: xherd's entries (command ends with `# xherd`) are replaced, the user's kept; invalid JSON refuses creation. Hook commands use the daemon's absolute `xherd` path; the token and job id come from the session environment.
- `Options::new` loads the built-in plugins (`xherd_plugin::builtins()`); clear `builtin_plugins` to test a missing runtime.
- A new file in `packs/xherd/` must be added to `xherd_flow::install::BUILTIN_FILES` (a test compares the folder with the list).
- Prompts teach XAP as plain `xherd <call>` inside backticks on one line, with concrete example values (never `"$XHERD_BIN"`: Claude Code cannot check a command with a variable and asks every time; the session `PATH` starts with xherd's folder and the worktree's `permissions.allow` lists the XAP subcommands, `XAP_ALLOW` in `create.rs`): the CLI test `prompt_calls_parse` parses every such call with clap, and `every_template_has_a_prompt` checks each manifest command has a `commands/<name>.md`.
- `xherd install` runs in the daemon (`POST /api/v1/install`), so commands land where the jobs run (user level, per the pack's `install.<runtime>.commands.to`). Run it once before the first job; nothing installs automatically yet. Tests call `Daemon::install` with their own `env` closure: never let a test resolve the real `HOME`.
- `Git::diff_proposed` stages the proposed files into a temporary `GIT_INDEX_FILE` (with `--force`, so proposed ignored files show) and never touches the worktree's index; paths are literal (`--literal-pathspecs`). Output is capped at 4 MiB by `exec::run` (silently truncated). A file over `DIFF_FILE_LIMIT` (8 MiB) is never staged or read (staging hashes it whole and stores the blob: a 6 GB heap dump made the Changes panel take minutes): it gets a `diff --git` header and a `Not shown: <path> is <size>, over the <limit> limit` line (`TOO_LARGE`), which the UI shows as `too large` and the commit tripwire turns into a hold (`not checked for secrets: …`). Tracked files go through plain `git diff` and have no limit.
- `approve` takes an optional `expect` (document → hash the UI read, from `GET /file`); a mismatch refuses with `changed_since_read`, so a UI approval covers exactly what was shown. The CLI sends none (hashes what is on disk).
- A runtime `Notification` while the job is stopped (`waiting-input`, `idle`) is an idle reminder (Claude Code: `notification_type: idle_prompt`, about a minute after a stop) and changes nothing; only mid-turn notifications (permission prompts) or `report --state blocked` set `blocked`. A blocked job cannot be approved.
- `Job.visited_stages` records every stage the job entered (added in `Actor::commit`, so every stage change counts); the UI shows earlier stages missing from it as skipped. Jobs saved before the field existed get it rebuilt once from their `xap.stage.enter` / `xap.gate.open` events when their actor starts.
- A question gate (`xherd ask`) is not approved: `xherd send` while it is open is the answer, clears the gate and logs `user.answer`.
- Toolchain defaults (R-653, issue #19): `toolchainDefaults` (config, tool → version, read at daemon start into `ActorSettings`, so `restartNeeded` applies) is what `toolchain::plan` uses for a tool with no version file (`file` = `xherd default`; version files always win). The plugin page (Settings → Plugins → click a card, `#/settings?tab=plugins&plugin=<name>`; the old Toolchains tab is folded into it) shows the plugin's settings and, for a toolchain, its tools (`components/Toolchains.svelte` with a `plugin` prop, `GET /toolchains`, `POST /toolchains/install`, `xherd_daemon::toolchains`): a tool's version dropdown comes from the manifest's optional `list` argv (one version per line, best first; `GET /toolchains/{tool}/versions` runs it in the container as the agents' user, 60 s, marks each version installed through `resolve`; the sdkman snippet now reads `sdk list java`'s four-column table, checked against the real one in the container) and falls back to a text box natively or when the list fails. It sets the default and installs a version in the container only, in the plugin-login tmux session shown at `/ws/setup/plugin-login` (one terminal for logins and installs). Not done: listing installable/installed versions, the Welcome step.
- Toolchains (R-652): at every session start (`Actor::session_argv`, also for fresh sessions) the daemon writes `.xherd/toolchain.json` from the worktree's version files and starts `xherd toolchain exec -- <launch>`; no version files = the runtime starts directly and the plan file is removed. Installing happens only with `XHERD_SANDBOX=1` in the daemon's environment (`Options::sandbox`). `exec::Cmd::inherit_output` shows install logs live in the window. The final `exec` of the runtime is the second exception to `exec::run`.
- Container mode (`XHERD_SANDBOX=1`, set by the image): toolchains install, the xherd commands are installed at every daemon start, `XHERD_BIND` overrides `config.bind` (`0.0.0.0`), and `XHERD_LOCAL_PEERS` (the gateway, from `xherd init`) counts as loopback for local rights (`Daemon::local_peers`). Safe only because compose publishes the port on the host's `127.0.0.1`. Without a runner the daemon and the jobs share one user (Setup check `single-user` says so); with one, the `runner` check pings it on every run.
- Never write into the real `$HOME` from code that tests start: the managed gitconfig goes to the data root unless `sandbox`; `Daemon::start` with `sandbox` installs commands with the process env, so tests never set `Options::sandbox`.
- Job tokens carry `hooks`, `xap` and `credential` scopes; `POST /git/credential` takes the local user or such a token.
- `Tmux::send_text` pauses 300 ms before each Enter: typed text and Enter sent back to back are taken as one paste by Claude Code and the Enter is dropped (the delivery retry then rescues it 10 s later).
- Supervisor messages carry `oneshot` replies straight to the caller; the supervisor never awaits an actor.
- A bearer token this daemon never issued, on an otherwise local request, is ignored (the host CLI of a native install sends its own token to the container); job and revoked tokens are still refused.
- Local browsers get full rights by address (loopback peer, local Host, no proxy headers) **and** a local or absent `Origin`: a request carrying another site's `Origin` is refused (no cross-site requests or websockets). In the container (`sandbox`) loopback does **not** count, because that is where the jobs are (R-1203, T2): only `local_peers` (the gateway the published port arrives from) has address rights, and the CLI there needs its user token (an unissued token is no longer ignored on loopback). Needs the engine to show browser traffic as the gateway: checked on Colima, **not yet** on Docker Desktop or Linux. The user split (daemon vs jobs) and `access: device` pairing for servers are the rest of R-1203 (branch `m4-user-split`).
- Two users in the container (R-1203, branch `m4-user-split`; design §8.4): `xherd init` creates `xherd-daemon` (ids from 10001, own volume `xherd-data` at `/var/lib/xherd-daemon`, `data/` 0700, `shared/` readable), starts `xherd runner` as the agents' user, then drops to the daemon's user (PATH = system dirs only, umask 002, in the host's group). `XHERD_RUNNER` makes the daemon send `Cmd::as_agent()` commands and `runner::{read_file, write_file, mkdir, find_in_subdirs_as_agent}` there (git, `verify:`, host/plugin commands and checks, the git-access doctor's ssh/git calls, the runtime's trust and hook files, pack commands, transcripts, `info/exclude`, clone cleanup); all of them act in place without a runner (native, tests). `XHERD_AGENT_<NAME>` (`XHERD_AGENT_HOME`, `XHERD_AGENT_PATH`) is what `runner::agent_env` returns instead of the daemon's own `HOME`/`PATH`: use it wherever the value is the jobs' (pack destinations, session PATH). The runner also supervises the tmux server (`--tmux`, socket `/run/xherd/tmux.sock`, `Tmux` uses `-S` for a path; the daemon's user gets in through `server-access` set by the runner, not by the config file, which tmux reads only when the first client connects); the runner opens its own socket only after that access is set (or 20 s), since the daemon starts sessions as soon as the runner answers: a resume at start once failed with `Permission denied` on the tmux socket and left the job in `error`). Shared, not through the runner: each worktree's `.xherd/` (`runner::mkdir`, mode 2775), `<workspace>/{worktrees,repos}`, `/run/xherd` (sockets and the hook queue, `XHERD_QUEUE`, mode 0660 when set). The daemon reads worktree files as itself: they must be group/world-readable. The managed gitconfig is `$XHERD_SHARED/gitconfig`. A CLI run as `xherd-daemon` finds `/var/lib/xherd-daemon/data` by itself (`Paths::from_env`); run as the agents' user it has no token (that is the point). Checked on Colima (processes, 401 on loopback, isolation, shared tmux, queue, job creation and diff); Colima's mounts do not enforce ownership, so **file permissions need a Linux host**. Not done: a Setup check for a runner that dies after start, `access: device` pairing (server milestone), per-user `docker exec` hints in `xherd docker doctor`.
- `config.json` is saved under `Daemon.config_write` (Settings and Git access both load–modify–save it), `secrets.json` under `secrets_write`; take the lock from the load to the save.
- The plugin name `git` is reserved: `secrets.json` keeps the Git-access host tokens under that key, in the plugins' namespace.
- External plugins and the two-user container (R-545, `xherd_daemon::plugin_dirs`): plugin commands, checks and hooks run `as_agent`, i.e. as the agents' user (so they can use the jobs' `gh`/`glab`/… logins and cannot read the daemon's files). That user cannot enter the daemon's private `data/`, so at daemon start `<data>/plugins` is copied to `$XHERD_SHARED/plugins` (folders 0755, files 0555 with an execute bit else 0444, symlinks skipped, 64 MiB cap per plugin; a plugin folder that cannot be copied is left out and listed as broken, the others load) and the registry loads from the copy; a plugin's config and state folders are under the agents' home (`~/.local/share/xherd-plugins/{config,state}/<name>`, the plugin creates them). A plugin added to `<data>/plugins` needs a daemon restart to be copied; plugin install must call `plugin_dirs::mirror` too. Backups do not include those two folders in the container.
- Debug builds serve `ui/dist` from disk (rebuild the UI, reload the page); release builds embed it at compile time, so build the UI before `cargo build --release`.
- "Viewed" marks (spec §16): the Changes panel has a Viewed checkbox per file; the UI fingerprints the file's diff (`fingerprint` in `Changes.svelte`, opaque to the daemon) and `POST /jobs/{id}/viewed {path, fingerprint}` stores it in `diff_viewed` (no fingerprint clears it), `GET /jobs/{id}/viewed` returns path → fingerprint; a changed diff un-marks the file. Marks are only for the UI, nothing gates on them.
- Diff preview (#26): the Changes panel has a Preview/Diff toggle for `.md`, `.html` and image files (`components/FilePreview.svelte`), only for the commit awaiting approval (no sha yet), whose files are what is in the worktree (`GET /file`, which gives images as `dataUrl`). Claude Code grabs the mouse, so selecting needs Shift+drag (Option+drag on a Mac, `macOptionClickForcesSelection`); a selection is copied to the clipboard at once; http(s) links (plain URLs and OSC 8) open in a new tab on click (`linkHandler` for OSC 8; plain URLs through `lib/termLinks.ts`, our own link provider, which also joins a URL over rows: those xterm wrapped and those a TUI broke itself, i.e. the URL fills its row to within `EDGE` (12) columns of the edge and the next row goes on with URL characters after its indent; Claude Code breaks rows about 8 columns early, so xterm's web-links addon only linked the first row). tmux always runs with `-u` (`Tmux::server_args`) and the image sets `LANG=C.UTF-8`: with no UTF-8 locale tmux draws every non-ASCII character as `_` (Claude Code's logo showed as underscores in the container).

- Container/terminal-server restart: `Daemon::start` reconciles with `recover` (`TickKind::SessionCheck { recover: true }`). A live job whose tmux session is gone is **parked** when it waits at a docs/commit gate (approving works, the fresh session starts with the next command), else it gets `session-lost` and is resumed like `Resume` (pack `resume` command). The periodic (60 s) reconcile still fails a vanished session (`error`), since then the job really died.
- xherd steps are new sessions with no history: `memory.md` (State / Decisions / Code map / Watch out, `FORMAT.md`) is what carries over, so each command reads it first and rewrites it before its gate. Keep that wording when editing the commands (D23).
- Resume (`Actor::prepare_resume`, used by the Resume action, restart recovery and auto-resume): the pack `resume` command is typed, and when the runtime plugin's `data.terminal.resume` (`--resume {session}`, transcripts folder + file) finds the last session's transcript, `claude --resume <id>` continues the conversation. A resume that never reached `session-start` is followed by a clean session. A session that vanishes while the daemon runs is auto-resumed at most `AUTO_RESUMES` (2) times per hour, then stays `error`.
- Commit identity (`gitUserName`/`gitUserEmail`, live): written to the managed gitconfig as `[user]`; `gitIdentities` (`scope` = `host[/owner]`) become `includeIf "hasconfig:remote.*.url:…"` blocks (HTTPS, scp-like and ssh:// patterns, git ≥ 2.36) pointing at `identities/N.gitconfig` next to it, so the identity follows the remote, not the path. Matching is case-sensitive, as git does it. Credentials are still one per host: a second account on the same host needs its own token handling (not done).
- Commit gates: on approval the actor itself runs `Git::commit_paths` (`git add --all -- files` then `git commit --only -m message -- files`, hooks run, 300 s timeout, inline in the actor: a deliberate exception to "slow work returns as WorkDone" because approve answers the UI with the result). The message is `Commit.message` (the job's `--message`, else the subject) or the user's edit (`approve` body `message`). Success: commit `done` + sha (a later `commit done` with the same sha is a no-op). Failure: git's output in `.xherd/commit-error.txt`, status stays `approved`, and `/xherd:commit C01` has the job fix and commit.
- `verify:` must be one runnable shell command. `tasks sync` (and `task done`) check it with `sh -n` and refuse `verify_invalid` before the tasks are approved (editing `tasks.md` after approval re-opens the gate); exit 126/127 at run time gets a hint in `verify_failed`.
